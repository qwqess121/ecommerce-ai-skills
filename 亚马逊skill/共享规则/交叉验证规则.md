## 零、为什么需要这一节

`深度分析层.md` 已给出诊断：**「单时点、单口径、单来源的报告必然是薄的。」**

但必须补一句：**「厚」和「真」是两件事。** 加时间轴、加下钻、加竞品对照能补厚度，补不了真伪——一条结论若只由一个来源支撑，它再厚也只是**一个来源的错**。

**已发生的三起单源误判（2026-09-18 复核）：**

| 误判结论 | 单源怎么骗过我们 | 换源后 |
|---|---|---|
| 「头号流量词 `car air freshener` 无 SP 覆盖」 | 只看 Sif **ASIN 级** `sp_rank: null` | 换 **Campaign 级**口径 → 实际有大量投放，只是**投放载体不是被审计的 ASIN** |
| 「`B0CYLN5HGL` 与 `B0CW9231N3` 是否同变体组」 | 只看后台 `parentAsin` 字段（只挂在其中一侧） | **双向入口**调 Listing 级工具 → 返回完全相同的 25 变体、总分同为 792,389.67 |
| 「本品差评率 31.6% 是品类宿命」 | 只看本品自己 | 引入 Vetuslumen（385 个评分仅 **6 条**差评，1.6%）→ **证伪** |

**共同点**：单源不一定是错的，但**单源错了你无法知道**。
**第二源的作用不是"确认"，是"提供被推翻的机会"。**

## 一、独立性判定（最容易搞错的一步）

> **同一工具调两次不是交叉验证。同厂的不同工具也不是。**

独立性只看一件事：**两个来源的底层采集方式是否不同。**

| 组合 | 独立？ | 原因 |
|---|---|---|
| Sif `sp_rank` vs Sif `adRankHistory` | ❌ **不独立** | 都是 Sif 算法推算，同一套底层数据 |
| Sif vs 领星 | ✅ 独立 | 算法推算 vs 卖家后台真实数据 |
| 领星 vs 卖家精灵 | ✅ 独立 | 后台真实数据 vs 第三方页面爬取 |
| 卖家精灵 `traffic_keyword` vs 卖家精灵 `review` | ⚠️ **弱独立** | 同厂，但采集对象不同（页面前台 vs 评论区）。**可作补充，不算双源** |
| MCP 数据 vs 亚马逊前台人工查看 | ✅ **最高权威** | 用于终极复核 |

**三个权威层级**（矛盾时参考，但**先看第五节判断是不是真矛盾**）：

```
① 卖家中心 / 领星后台真实数据      ← 最接近事实
② 第三方页面快照（卖家精灵）
③ 算法推算分数（Sif 曝光分 / 流量分）
```

## 一·B、数据时效性与取数纪律（**报告数据必须对得上**）

> **这一节是血债换来的。** 2026-09-18 用户拿模块一报告与领星后台逐项核对，发现数字对不上：
>
> | 指标 | 报告写的（错） | 领星后台实际 | 差 |
> |---|---|---|---|
> | 销量 | 73,296 | **73,882** | −586 |
> | 销售额 | $1,003,957.90 | **$1,011,916.73** | −$7,958.83 |
> | 毛利率 | 12.47% | **12.21%** | −0.26pt |
> | 广告花费 | $125,070 | **$127,159.09** | −$2,089 |
> | ACOS | 31.10% | **31.08%** | +0.02pt |
>
> **根因不是算错，是根本没取数。** 这行数字从 `v2 修订版` 一路抄到 `深度版`、再抄到 `规则版`，三代沿用一个旧快照，从未重新拉取。上一轮声称"实时复核了数据"，实际只复核了 Sif 的 ASIN 级数据，**领星的自有资产数据直接沿用了旧报告**。

### 铁律（五条，无例外）

| # | 条款 | 说明 |
|---|---|---|
| 1 | **现场重取** | 报告中**任何**来自 MCP / 后台 / 第三方工具的数字，必须**在本次生成报告时重新调用工具拉取**。**禁止**沿用上一版报告、历史快照、记忆值、上一轮对话里的数字 |
| 2 | **记录快照时点** | 每个数据块必须标注 **取数时间戳 + 数据窗口**（例：`领星 2026-08-18~09-17，取数于 2026-09-18 14:32`）。同一指标跨版本比对时，**必须同口径同窗口** |
| 3 | **交付前 diff** | 交付前必须把报告里每个数字与**最后一次拉取的原始返回**逐项 diff。**不一致即阻塞交付**，修正后才发 |
| 4 | **禁止"继承式正确"** | 不得因"上一版这么写的"而认为数字正确。**历史报告不是数据源，只是历史结论** |
| **5** | **🔴 头部元信息与数字同步刷新（含页脚）** | 刷新数字时，**必须同步刷新报告头部的元信息块**（`取数时间` / `数据窗口` / `数据时效` / `取数凭据` 四行）；**渲染后 HTML `<footer>` 的取数时点 / 数据时效也必须跟随**（须由构建脚本从 md 头部**自动提取**，禁止硬编码）。**"数字是新的、时间戳是旧的" 与 "数字是旧的" 同等不合格** —— 前者更隐蔽，会让看报告的人以为数据没更新。**交付前必跑 6.3.4 的头部元信息核对，ERR 必须为 0**（它同时查 md 头部**与** HTML 页脚） |

#### 铁律 5 的执行细则（2026-09-23 立 · 血债见下）

**背景事故**：2026-09-23 全量重取，**五份报告的数字全部刷新了，但只有模块 4 的头部时间戳被同步改掉**——模块 1/2/3/5 头部仍写 `取数时间 2026-09-21 10:55–11:40 ｜ 数据时效 MCP 更新至 2026-09-20`。用户一眼看出并质疑「为什么还是之前的」。

**根因**：那一轮只做了**单元格级数字替换**，**漏改了头部元信息块**。数字（18,990 / 2,106 / #77 / 1,461）确实是 09-23 的新值，但头部还挂着 09-21 的日期 → **报告自相矛盾**。

**必须做的三件事**：

| # | 动作 | 判据 |
|---|---|---|
| 1 | **头部四行与数字同批更新** | 刷新脚本必须把 `取数时间` / `数据窗口` / `数据时效` / `取数凭据` 当作**同一次替换任务的一部分**，不得只改表格数字 |
| 2 | **跨模块一致性** | 同一次全量刷新后，**所有模块的取数日必须相同**。不一致 = 漏改头部 |
| 3 | **凭据与头部对齐** | 头部 `取数凭据` 指向的 `_raw/xxx-YYYY-MM-DD.md`，其日期必须 **= 头部取数日**。对不上 = 凭据与头部脱钩 |
| 4 | **🔴 页脚与头部同源** | 渲染后 HTML `<footer>` 的 `取数时点` / `数据时效` **必须由构建脚本从 md 头部自动提取**（禁止硬编码）；五模块页脚日期必须 **= 各自头部取数日**。页脚硬编码 = 头部修了页脚还挂着旧日期（2026-09-23 实测踩中） |

**⚠️ 例外：口径不同的项不随重取，必须显式标注**

若某数据块的口径/窗口与本次重取范围**不同**（实例：模块 1「自有经营盘」是**全店**口径、窗口 `2026-08-18~09-17`，而模块 2/4 是**单品**窗口 `2026-09-06~09-22`），它的数字**不应被重取**——此时**正确做法是写明口径差异**：

> ✅ 正解：`窗口 2026-08-18 ~ 09-17，2026-09-21 取数 / 2026-09-22 复核（⚠️ 本项为全店口径、窗口与模块 2/4 的单品窗口不同，故不在 2026-09-23 单品全量重取范围内，数值沿用复核结果）`
>
> ❌ 反解：**把日期静默改成 09-23** —— 那是另一种失真（凭空宣称重取过）
> ❌ 反解：**原样保留旧日期不作任何标注** —— 读者无法分辨"没重取"还是"忘了改"

**自动化巡检器（强制交付门槛）**

``6.3.4 的头部元信息核对``

它检查：① 跨模块取数日是否一致 ② 凭据文件名日期是否 = 头部取数日 ③ 数据时效早于取数日时是否标了 T+1 ④ **HTML 页脚日期是否 = 对应 md 头部取数日**（2026-09-23 追加，见下「页脚同源」）。
**`ERR = 0` 才算过**（`WARN` 为 T+1 滞后提示，属预期，不阻塞）。**退出码非 0 即阻塞交付。**

**🔴 页脚必须与头部同源（2026-09-23 追加 · 同一事故的第二形态）**

上一条铁律讲的是 **md 头部**；但**渲染后的 HTML `<footer>` 还有一份「取数时点 / 数据时效」**。若它由构建脚本**硬编码**，就会出现「md 头部修好了、页脚仍挂旧日期」——**同一份报告上下自相矛盾**，且 6.3.4 的头部元信息核对 初版只扫 md、**完全看不见**。

- ✅ 正解：页脚的取数时点 / 数据时效 **从 md 头部自动提取**（`build.py` 的 `extract_footer_meta()`），头部一改页脚必跟着变，**物理上不可能不一致**。
- ❌ 反解：在 `build.py` 的模板里写死日期（曾写死 `2026-09-21 10:55–12:35 ｜ MCP 更新至 2026-09-20`，五模块共用一份 → 一次性全错）。
- ❌ 反解：页脚留空话（`（见头部）`）—— 模块 3 头部原本**没有** `**数据时效**` 字段，须先给它补上，而不是让页脚显示空话。

> **通用教训**：同一份事实（取数日）**在报告里有几个落点，就要全部覆盖**。修字段时先 `grep` 该字段在 **md + html + 构建脚本** 里的**全部出现位置**，确认修的是「源」而不是「一处副本」。

### 反模式清单（见到即判不合格）

- ❌ 「上轮已核对过数据」→ 核对过的是**那个时点**的数据，不是**这次**的
- ❌ 「只改了结论文字，数字没动」→ 数字没动 = 没重取 = 不合格
- ❌ 「MCP 数据会漂移，取到旧的很正常」→ 漂移更要**现场取 + 标时点**，不是拿旧的
- ❌ 报告里出现**无法追溯到某次工具调用**的数字 → 视为捏造
- ❌ **「数字刷新了，但头部取数时间/时效/凭据没跟着刷新」** → 头部与正文自相矛盾，**同等不合格**（2026-09-23 实测：5 模块里 4 个漏改）
- ❌ **「头部刷新了，但渲染后 HTML 页脚的时间戳没跟着刷新」** → 页脚由构建脚本**硬编码**时必踩；**头部与页脚自相矛盾**（2026-09-23 实测：五模块页脚全挂 `2026-09-21 10:55 / MCP 更新至 2026-09-20`）。页脚**必须从 md 头部自动提取**
- ❌ **「口径不同的数据块，把日期静默改成最近一次重取日」** → 凭空宣称重取过，比不标更坏
- ❌ **「只修看得见的那一处副本」** → 同一事实（如取数日）在 md 头部 / HTML 页脚 / 构建脚本模板里**有多处落点**，改前必须 `grep` 全部出现位置
- ❌ **行动清单的"改成什么"写成"产出《XX表/记录/清单》1 份"**（比如"拉取评论增速，产出《XX竞品追踪表》"、"建立《XX季度盯盘表》"）→ 这是把"做研究/写文档"本身当成行动，读者要的是"这件事最终会带来什么运营/产品/定价上的实际改变"，不是多一份内部文档。**判断标准**：这一条执行完之后，除了"多了一份文档"，有没有发生任何看得见的业务动作（调价/改图/改文案/上新/暂停广告/设预警阈值等）？没有就要重写——把"产出报告"改成"做完调研后，直接触发什么动作、在什么条件下触发"（例：不写"产出COCODOR追踪表"，写"给COCODOR设置评论数预警，破50条立即启动A1提速评估"）。签发采购/打样工单、发起外部合规咨询这类**本身就是业务动作**、文档只是动作的自然凭证的，不算这一条要打的对象
- ❌ **章节标题挂"（方向A）""（L4）"这类结构/层级标签**，当上级已经有"## 方向A·垂直类"这种banner分隔时，每个子标题没必要再重复标注属于哪个方向/哪个分析层——只在banner或第一次引用某分析方法时说明一次，其余标题保持干净
- ❌ **章节开头写"本节是XX流程的StepN，下设A/B/C三个子节，为后续第X-Y节提供基准"这类流程/框架说明**——直接从子节内容开始，读者不需要被预告"这一节的结构是什么"
- ❌ **同一批对象（比如20个竞品）的基础字段（价格/评分/月销/BSR等）被拆进多张字段有重叠的表**（比如"真竞品表"+"类目Top表"各自列一遍基础字段，"广告结构表""5维度对比表"又各自把价格/评分抄一遍）→ 应合并成**一张总表**，用"档位/分类"列区分对象类型，字段取并集；确实是**不同维度、不同用途**的表（比如"竞品判定"的四维硬门槛通过/剔除表 vs "本品自己的费用瀑布"这种单体诊断）不算这一条，不要为了合并而合并
- ❌ **单独设"分档读法"这类"教读者怎么看这张表/这个分档"的说明小节**（比如"分档读法A·真竞品档""分档读法B·类目Top档"）→ 这也是过程/方法说明的一种，读者应该能直接看懂表格和结论，不需要专门教程；这类小节直接删除，如果分档本身的判定逻辑需要说明，写进对应模块的 `SKILL.md`
- ❌ **正文里写"用了哪个 MCP 工具/字段名/查询参数"**（如"Sif `market_get_keyword_competition` 的 `organic_share` 字段"）→ 读者是老板/运营不是工程师，这类技术取数细节只写进对应模块的 `SKILL.md`，正文只留数字和结论（详见 6.3.1 节附录约定后的说明）
- ❌ **报告正文里写"过程/版本叙事"**：任何"上一版/上版/本轮修正/本轮新增（回应XX规则）/结论调整为/本节是对用户反馈的重做/由X降为Y/置信度由高置信下调一档"这类交代**我们自己编辑过程、版本演变、为什么这样改**的元话语，都不该出现在"老板决策版"正文里——老板只关心**现在的结论和数字是什么**，不关心这份报告的编辑史。发现这类表述，直接删掉叙事部分，只保留**当前结论本身**（该有的置信度/样本量/证据来源等**事实性**信息要保留，只是不能用"版本对比"的方式讲出来）。判断标准：读这句话需要知道"上一版写了什么"才能懂，就是过程叙事，必须删或改写成不依赖历史对比的独立陈述（2026-09-28 实测：模块一/二/五多处踩坑，含头部"本次二订/三订"变更日志、字段名勘误说明、差评置信度调整的"由X降为Y"表述）

### 领星类后台数据的特别要求

- 必须用 `query_product_performance_asin_lists` 的 **`total_sum`** 字段取全店汇总，**不要**自己把品类行加总（口径易错）
- 必须记录 `stat_scope`（店铺范围）、`currency_code`、`date_type`、`summary_field` 四个口径参数
- 同一窗口两次拉取出现漂移（实测出现过 73,692 / 73,882）→ **以本次拉取值为准并标时点**，不要取平均

## 二、独立源矩阵（按结论类型查表）

**执行方式：任何一条要写进「结论 / 建议」的话，先在本表找到它属于哪一类，然后两个源都要跑。**

| 结论类型 | 主源 | 独立第二源 | 备注 |
|---|---|---|---|
| 广告花费 / ACOS / ROAS 规模 | 领星 `ad_campaign_report` | Sif `ads_get_asin_ad_traffic_trend`（广告占比演变） | 两口径不同，**并列呈现，不取平均** |
| 关键词广告覆盖（有 / 无） | Sif **ASIN 级** `market_get_asin_keyword_signals.sp_rank` | 卖家精灵 `traffic_keyword.adPosition` | **否定结论必须双源**（见第三节 #4） |
| 广告槽位排名 | Sif **Campaign 级** `adRankHistory.rank` | 卖家精灵 `traffic_keyword.adPosition.index` | 两者是不同口径，见三口径纪律 |
| 自然位排名 | Sif `naturalRankHistory` | 卖家精灵 `traffic_keyword.rankPosition` | 用于判定"空值 = 无自然位"还是"数据缺失" |
| 变体 / Listing 归属 | Sif `ops_get_listing_traffic_structure`（**两个入口各调一次**） | 卖家中心变体管理页（人工） | 双入口一致 = 置信度 B；后台字段矛盾 → 强制人工复核 |
| 成本 / 利润 | 领星 `query_order_profit_list` | Sif `market_estimate_profit_threshold` 反推上限 | 反推值与实算值差 >30% 必须说明 |
| 评论痛点 | 卖家精灵 `review`（1–3★ 池） | **竞品同口径** `review` + 亚马逊前台 | **必须带竞品对照**，单看本品无法区分类目通病 |
| 需求 / 趋势方向 | Sif `market_get_keyword_root_trend` | 卖家精灵 `google_trend` / `asin_sales_trend` | 方向相反时优先信长窗口 |

## 五、矛盾处理三分支

> ⚠️ **最常见错误：把「口径不同」当成「矛盾」去调和。**
> 两个数字不一样，可能只是**回答了两个不同问题**。
> 实例：`60.18%`（单个 campaign 占账户广告**曝光**的比例）与 `71.99%`（占 Listing **流量分**的比例）**不是矛盾**，各自都正确。
> **先判定是不是同一口径，再谈矛盾。**

| 分支 | 触发情形 | 处理方式 | 报告怎么写 |
|---|---|---|---|
| **A · 标注存疑** | 矛盾不影响当前行动 | 并列两结果 + 标注"待确认" | 两个数字都写，标清各自口径与含义；**不下单向结论** |
| **B · 加权取一** | 有明确权威层级差（如后台 vs 算法推算） | 采用高权威源，写明理由 | 写结论 + 脚注「依据后台真实数据；算法推算为 X，差异原因 Y」 |
| **C · 强制再取证 + 用户复核** | 涉及不可逆动作，或矛盾无法在数据层解决 | **暂停该条建议**，给用户一份《需人工复核清单》 | 结论标注"待卖家中心复核后生效"，**不写成可执行动作** |

**C 分支纪律**：**宁可给一条"待确认"，也不给一条错的执行建议。涉及花钱的动作，不确定就不给。**

**6.3.5 🔴 线上交付的缓存纪律（2026-09-22 事故 · 比"忘记发布"更隐蔽）**

**症状**：报告已发布、6.3.4 的核对全部通过、带 `?nc=` 回读也全绿，**用户在浏览器里看到的仍是旧版**（模块三表格 ASIN 是纯文本、点不动）。

**根因**：线上是 **CloudStudio Gateway**，缓存键 = **完整 URL + `Accept-Encoding`**，`identity / gzip / br` **三份分开缓存**，且**重新发布不会失效已缓存的变体**。真实浏览器（Chrome / Edge / Safari）**全都发 `br`** → 全拿旧副本。而先前的回读用 `urllib` 默认请求（**不发 Accept-Encoding**）→ 读 identity 新副本 → **假绿**。

| 资源 | identity（无压缩） | **br（浏览器拿到的）** |
|---|---|---|
| `module-2.html` | 164 个商品链接 | **14 个** |
| `module-3.html` | 112 个商品链接 | **1 个** |
| `assets/report.css` | 12,001 字节 | **10,016 字节** |

**两条对策（都已固化）**：

1. **资源挂版本号**：`build.py` 产出 `ASSET_V`（构建时刻），写进 `<meta name="asset-v">` 并挂到 **CSS / JS 引用 + 所有站内跳转**（`nav.js` 读 meta 拼 `?v=`；`index.html` 由 `sync_index_version()` 自动同步）。**版本号一变 URL 就变 → 网关必然回源**，不依赖它的失效行为。
2. **回读必须带 `br`**：发布后用浏览器无痕窗口回读，**不要只用 `urllib + ?nc=`**。

- ⚠️ **裸 URL 的陈旧副本无法从外侧失效**，只能等它过期 → **分享时给站点首页链接**。
- 识别特征：br 响应带 `Age:` 头、`Last-Modified` 停在更早一次发布；加任意 `?参数` 后 `Age` 消失、内容变新 → 即 URL 键缓存。
- 用户说"还是旧的 / 点不动"时，先用无痕窗口回读，分清**本地 / 没发布 / 网关缓存**三态，**别急着改内容**。

**6.3.6 术语与评判标准：只在模块主 SKILL 维护一处（2026-09-23 立）**

**问题**：模块主 SKILL 与子 skill 会大量出现专业名词（长尾词 / ACOS / TACOS / 差评差集 / 事实卡 / Buy Box / A9 四因素…）与判定阈值（覆盖率 ≥90%、差距 ≥3 分、ACOS>200% 降 30–50%…）。若**每个文件各写一套定义**，必然出现**同一名词两处口径不一、后期改一处漏一处**（典型案例：库内曾出现同一指标 3.89% 与 4.05% 并存）。

**规则（强制）**：

| 规则 | 说明 |
|---|---|
| **术语表只在模块主 SKILL** | 每个模块的 `X模块/SKILL.md` **必设一节 `## 术语表（老板 / 新人必读）`**，逐条给出该模块专业名词的**中文名 + 英文名 + 定义 + 计算口径 + 判定阈值 + 出处工具**（例：`**TACOS（Total ACOS）**：广告花费 ÷ 总销售额…`） |
| **评判标准也只在模块主 SKILL 汇总** | 模块主 SKILL 必设 **`## 评判标准速查表`**（检查项 / 数据来源 / 判定阈值三列）。子 skill 的详细清单里可保留**本 skill 专属**的内联「评判标准」，但**通用阈值不得另立一套** |
| **子 skill 只写指针** | 每个子 skill 须含一节 **`## 📖 术语（专业名词）查找`**，只写「定义见模块主 SKILL 的术语表 + 速查表」并给出主 SKILL 路径；**禁止在子 skill 重复定义术语** |
| ⚠️ **例外（脚本型 / 暂缓型）** | 纯脚本清洗类（跑脚本不产报告）与暂缓模块（模块六）按实际需要精简，但**仍须有术语表 / 指针，不得缺失** |

> **判据**：改一个术语或阈值时，只应改 **1 个文件**（模块主 SKILL）。若发现需要同时改 2 处以上，说明该内容被重复定义了，须合并到主 SKILL。

**落点**：本规则由 `交叉验证规则.md`（本节）承载；模块主 SKILL ×6 各设术语表 + 速查表；子 skill ×33 各设指针块。

**6.3.7 🔴 极简去重：三件套保留但瘦身（2026-09-23 第七轮 · 用户裁定「内容太多了，好多是重复的」）**

**背景**：6.3.2 / 6.3.2.1 强制"小结卡 + 清单表 + 成品交付"三件套后，报告**一度变厚**——成品块与正文**各写一遍**同一份内容、清单表「现状」列把正文数字**再抄一遍**。用户判定「太多了，而且好多是重复的」。**裁定：结构保留，内容瘦身**（不是取消三件套）。选项为三档（轻 / **中** / 重），用户选**中等**（目标 −30~35%，信息不丢失）。

| 规则 | 做法 | 判据 |
|---|---|---|
| **R1 · 清单「现状」列去重** | 「现状」列**只留关键判断词 + 指针**（如「偏低（见 3.1 表）」），**不再重述数字串** | 同一数字在正文表已出现 → 清单列**不得再抄一遍** |
| **R2 · 成品块去解释文字** | 📦 成品块**只留可复制正文本体**；块**外**的「理由：…」「说明：…」一律删（**代码块内不动**） | 成品块的价值是"能直接复制"，解释文字不影响复制 |
| **R3 · 同一数字只首次定义** | 某数字在**首次出现的表**写全，其他位置**只给指针** | 全报告集**同一数字只允许一处写全** |
| **R4 · 不动的清单（防过度删）** | 以下**一律不动**：小结卡 · 分析主表 · **三档六列结构**（三档必须齐全，空档写「（无）」）· **成品块的存在本身** | 它们是**决策内容**与**结构骨架**，不是冗余（**"一句话结论"/"验收口径"/"需要老板拍板事项"已于 2026-09-28 从本清单移除——这三者已确认整节删除，不再是"保留但瘦身"的对象**） |

> 🔴 **两个真实冗余源（本轮实测，引以为戒）** —— ① **正文与 `### 📦 成品交付` 代码块各写一遍**（模块五 A/B/C/D **四个提示词包 + 图片硬约束表 + 交付自检表 = 6 处双份**）；② **成品表与正文数据表逐字重复**（模块二 **4 张成品表**：竞品对比矩阵 / 差距归因 / 费用瀑布 / 互食矩阵）。**这两类才是"内容太多"的主因**，不是字多。

> ⚠️ **瘦身目标不是硬指标** —— 实测 **模块 2 −21% / 模块 5 −19%，模块 1/3/4 仅为个位数**。原因：模块 1/3/4 的体量本就是**强制保留的三档清单表**（结构性内容，R4 保护），**要凑到 −30% 只能删决策内容**，得不偿失。**宁可不达标，不删决策。**

> ⚠️ **瘦身改的是报告，规则里的话不要原样搬进报告** —— 报告**不解释"为什么删/为什么这样排版"**；新生成的报告直接产出瘦身后的形态，不再出现"本版精简了 X 处"这类元叙述（版本说明只写在头部信息块的本版说明里，一处）。

> **排版乱 = 读者抓不到结论。** 数字对得上但结构跳来跳去、同一建议讲两遍，等于把核对成本转嫁给用户。**同一句话写两遍，与"写得不清楚"是同一类问题 —— 都让老板多花一次核对成本。**
